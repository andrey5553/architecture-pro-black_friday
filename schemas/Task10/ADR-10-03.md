### **Контекст и описание проблемы**
Необходимо выбрать оптимальные стратегии обеспечения целостности данных для каждой сущности, 
мигрируемой в Cassandra, с учетом требований к производительности и консистентности.

### <a name="adr-10-03-proposal-solution"></a>**Решение**

#### 1. Обзор стратегий восстановления целостности

#### Характеристики стратегий

| Стратегия           | Когда срабатывает                      | Влияние на latency                   | Гарантии консистентности | Нагрузка на сеть |
|---------------------|----------------------------------------|--------------------------------------|--------------------------|------------------|
| Hinted Handoff      | При недоступности узла во время записи | Минимальное (асинхронно)             | Eventual consistency     | Низкая           |
| Read Repair         | При чтении с CL < ALL                  | Увеличивает latency чтения на 10-20% | Постепенное улучшение    | Средняя          |
| Anti-Entropy Repair | По расписанию (cron)                   | Не влияет на запросы                 | Полная консистентность   | Высокая          |

#### 2. Стратегии для корзин (carts)

#### Конфигурация таблицы
```cql
CREATE TABLE carts_by_session (
    session_id UUID,
    bucket_id INT,             -- Шардинг на основе product_id
    product_id UUID,           -- Clustering Key
    user_id UUID STATIC,       -- Общие данные для всей корзины
    quantity INT,
    unit_price DECIMAL,
    product_name TEXT,
    updated_at TIMESTAMP,      -- Обычное поле, а не ключ
    PRIMARY KEY ((session_id, bucket_id), product_id)
) WITH 
    default_time_to_live = 2592000
    AND gc_grace_seconds = 864000
    AND compaction = {'class': 'SizeTieredCompactionStrategy'}
    AND speculative_retry = '99percentile';
```

#### Выбранные стратегии

Основная: Hinted Handoff
```yaml
# cassandra.yaml
hinted_handoff_enabled: true
max_hint_window_in_ms: 10800000  # 3 часа хранения хинтов
```
#### Обоснование
Для данных корзины покупок, которые имеют короткий TTL (30 дней) и характеризуются 
высоким R/W соотношением с преобладанием операций обновления, выбран баланс между 
доступностью и согласованностью в пользу низкой задержки. Используется уровень 
согласованности LOCAL_QUORUM, что гарантирует сильную консистентность в рамках 
дата-центра без глобального блокирования. Риск временной недоступности реплики смягчается 
стандартными механизмами кластера: hinted handoff для коротких сбоев и 
read repair по необходимости, что достаточно для некатастрофичной потери данных в данном контексте.

#### 3. Стратегии для сессий пользователей

#### Конфигурация таблицы
```cql
CREATE TABLE user_sessions (
    session_id UUID,
    user_id UUID,
    created_at timestamp,
    last_activity timestamp,
    session_data map<text, text>,
    PRIMARY KEY ((session_id))
) WITH 
    default_time_to_live = 86400
    AND gc_grace_seconds = 864000;      -- 10 дней для tombstones
```

#### Выбранные стратегии

Основная: Оптимизированный доступ по первичному ключу с автоматическим сроком жизни
Таблица спроектирована для единственного критичного запроса — мгновенного поиска 
сессии по её идентификатору (WHERE session_id = ?). 
Структура PRIMARY KEY ((session_id)) обеспечивает прямое попадание в партицию без дополнительных поисков.

Стратегия согласованности: Уровень LOCAL_QUORUM на уровне приложения
Для операций чтения/записи используется уровень согласованности LOCAL_QUORUM, 
гарантирующий актуальность данных сессии в рамках локального дата-центра с минимальной задержкой, 
что критично для производительности аутентификации.

#### Обоснование
Для данных пользовательских сессий, имеющих короткий срок жизни (24 часа) 
и критичных к задержке операций аутентификации, выбран баланс в пользу доступности 
и низкой latency. Использование уровня согласованности LOCAL_QUORUM 
гарантирует актуальность данных при чтении без глобальных блокировок. 
Риск минимальной временной рассогласованности при сбоях приемлем, 
так как ущерб ограничен необходимостью повторного входа 
пользователя в систему, что не ведёт к потере бизнес-данных.

### 4. Стратегии для истории заказов

#### Конфигурация таблицы
```cql
-- Предполагается, что UDT уже создан: CREATE TYPE order_item (...);

CREATE TABLE order_history_by_customer_and_month (
    customer_id UUID,
    time_bucket TEXT,                 -- Формат 'YYYY-MM'
    created_at TIMESTAMP,
    order_id UUID,
    total_amount DECIMAL,
    status TEXT,
    items LIST<order_item>,           -- БЕЗ 'frozen'!
    PRIMARY KEY ((customer_id, time_bucket), created_at, order_id)
) WITH 
    CLUSTERING ORDER BY (created_at DESC)  -- Новые заказы в начале
    AND default_time_to_live = 0           -- История хранится вечно (или задать свой TTL)
    AND gc_grace_seconds = 864000          -- 10 дней
    AND compaction = {'class': 'TimeWindowCompactionStrategy',
                      'compaction_window_unit': 'DAYS',
                      'compaction_window_size': 30};
```

#### Выбранные стратегии

Основная: Регулярный полный repair (еженедельно)

История заказов — финансово значимые данные, требующие гарантированной консистентности. 
Выполняется еженедельный полный repair для всего keyspace (или таблицы) 
с использованием стратегии -pr (parallel) для скорости. 
Repair обязателен, несмотря на потенциальный большой размер, 
так как предотвращает накопление расхождений.

```bash
#!/bin/bash
# Еженедельный полный repair для таблицы истории заказов
# Запуск: repair_order_history.sh
KEYSAPCE="mobileworld"
TABLE="order_history_by_customer_and_month"

# Вариант 1: Parallel repair всей таблицы (рекомендуется)
nodetool repair -pr $KEYSAPCE $TABLE

# Вариант 2: Sequential repair с указанием DC (если нужно)
# nodetool repair -seq $KEYSAPCE $TABLE -dc datacenter1
```

Стратегия согласованности запросов: QUORUM

Все запросы к истории заказов (чтение и запись) выполняются с уровнем 
согласованности QUORUM (или LOCAL_QUORUM при мульти-DC). 
Это обеспечивает сильную консистентность для финансовых 
данных: чтение всегда вернёт актуальные данные с большинства реплик.

```java
// Пример в коде приложения
stmt.setConsistencyLevel(ConsistencyLevel.QUORUM);
```

Стратегия мониторинга и автоматизации

Внедрены алерты на пропущенные окна repair. 
Используется nodetool repair -inc только для срочного исправления конкретных проблем, 
обнаруженных мониторингом, а не как регулярная процедура.

#### Обоснование
История заказов содержит финансово значимые данные, которые хранятся годами 
и подпадают под требования регуляторов к аудиту и целостности. 
Для гарантии абсолютной точности и согласованности данных во времени 
выбран подход, сочетающий сильную консистентность на уровне каждого
запроса (QUORUM) с регулярными профилактическими операциями 
полного repair кластера. Это обеспечивает требуемый уровень 
надёжности без reliance на вероятностные механизмы.

### 5. Оптимизация Consistency Levels

#### Матрица выбора уровней консистентности

| Операция         | Корзины               | Сессии           | История заказов | Обоснование                                      |
|------------------|-----------------------|------------------|-----------------|--------------------------------------------------|
| Запись           | LOCAL_QUORUM          | LOCAL_QUORUM     | LOCAL_QUORUM    | Баланс скорости и надежности                     |
| Чтение обычное   | LOCAL_QUORUM          | LOCAL_QUORUM     | LOCAL_ONE       | Максимальная скорость/актуальность данных        |

## Преимущества выбранного подхода

1. Архитектура, ориентированная на паттерны доступа (Access Pattern-Driven Design)
2. Масштабируемость через превентивное шардирование (Sharding for Scale)
3. Управление жизненным циклом данных (Automated Data Lifecycle)
4. Явный контроль над согласованностью и надёжностью (Explicit Consistency & Reliability)

### **Альтернативы**

Альтернатива 1: Согласованность на уровне ONE для всех операций
Суть: Использовать CONSISTENCY ONE для всех запросов чтения/записи для минимальной задержки.

Альтернатива 2: Ручное управление repair (отказ от автоматизации)
Суть: Выполнять nodetool repair только при обнаружении проблем, без расписания.

Альтернатива 3: Единая агрессивная стратегия repair для всех таблиц
Суть: Применять одинаково частый и полный repair ко всем таблицам, включая те, что имеют короткий TTL (сессии, корзины).

**Недостатки, ограничения, риски**

| Риск                                 | Снижение рисков                                    |
|--------------------------------------|----------------------------------------------|
| Накопление несогласованности         | Регулярный (еженедельный/ежемесячный) полный или инкрементальный repair всего кластера. Это обязательная процедура, а не опция. |
| Потеря данных при сбое узла, превышающем window хинтов               | 1. RF >= 3 для критичных данных. 2. Использование LOCAL_QUORUM для записи (данные есть на 2+ узлах сразу). 3. Прием риска для данных, переживших окно хинтов: они будут восстановлены repair.         |
| Влияние repair-процесса на latency приложения         | 1. Инкрементальный repair. 2. -pr (parallel) флаг для ускорения. 3. Запуск в запланированные maintenance-окна. 4. Мониторинг метрик ноды во время repair.               |
| "Горячие партиции" (Hot Partitions) | Превентивный дизайн: использование bucket_id (для корзин) и time_bucket (для заказов) в Partition Key. Мониторинг ReadLatency/WriteLatency на уровне таблиц.       |
