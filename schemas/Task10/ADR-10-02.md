### **Контекст и описание проблемы**
Необходимо разработать детальную модель данных с оптимальной стратегией партиционирования 
для обеспечения равномерного распределения нагрузки и предотвращения "горячих" партиций.

### <a name="adr-10-02-proposal-solution"></a>**Решение**

### 1. Концептуальная модель для корзин (carts)

#### Структура данных и ключи
```cql
CREATE TABLE carts (
    session_id UUID,           -- Partition Key (но с bucket_id)
    bucket_id INT,             -- Искусственный ключ для шардирования (0-15)
    product_id UUID,           -- Clustering Key
    user_id UUID,
    quantity INT,
    price DECIMAL,
    product_name TEXT,
    product_image_url TEXT,
    updated_at TIMESTAMP,      -- Обычное поле, а не ключ
    status TEXT STATIC,        -- Общий статус для всей корзины
    PRIMARY KEY ((session_id, bucket_id), product_id)
) WITH default_time_to_live = 2592000
   AND compaction = {'class': 'SizeTieredCompactionStrategy'};
```

#### Обоснование выбора ключей
* Partition Key (session_id, bucket_id):
  * Обеспечивает равномерное распределение: UUID генерируется случайно для каждой сессии.
  * Добавлен bucket_id. Это главная защита от горячих партиций. 
  * При добавлении товара bucket_id = hash(product_id) % 16. Активность распределяется по 16 партициям.
  * Состояние товара в корзине хранится в одной строке.
  * SizeTieredCompactionStrategy: Предсказуемая стратегия для частых обновлений данных.

* Clustering Keys product_id:
  * product_id предотвращает дубликаты при одновременных обновлениях

Для хранения истории изменений по заказу, лучше сделать отдельную структуру данных

```cql
CREATE TABLE cart_audit_log (
    session_id UUID,
    event_time TIMESTAMP,
    product_id UUID,
    event_type TEXT, -- 'ADD', 'UPDATE_QUANTITY', 'REMOVE'
    old_quantity INT,
    new_quantity INT,
    PRIMARY KEY ((session_id), event_time, product_id)
) WITH CLUSTERING ORDER BY (event_time DESC)
  AND compaction = {'class': 'TimeWindowCompactionStrategy'};
```

#### Паттерны доступа
  ##### Получить 20 последних событий в корзине (добавление, изменение кол-ва)
  ```cql
  SELECT * FROM carts WHERE session_id = ? ORDER BY updated_at DESC LIMIT 20;
  ```

-- Обновление товара в корзине
UPDATE carts SET quantity = ? WHERE session_id = ? 
  AND updated_at = ? AND product_id = ?;

  ##### Получить все изменения в корзине за последний час
  ```cql
  SELECT * FROM carts WHERE session_id = ? ORDER BY updated_at DESC LIMIT 20;
  ```
  ##### Получить все изменения в корзине за последний час
  ```cql
  SELECT * FROM carts WHERE session_id = ? ORDER BY updated_at DESC LIMIT 20;
  ```
  ##### Запрос для получения актуального списка товаров в корзине (Это сложная, ресурсоёмкая и медленная операция)
  ```cql
  SELECT * FROM carts WHERE session_id = ?;
  ```
  ##### Обновление товара в корзине
  ```cql
  UPDATE carts_by_session 
  SET quantity = ?, updated_at = toTimestamp(now())
  WHERE session_id = ? AND bucket_id = ? AND product_id = ?;
  -- где bucket_id = hash(product_id) % N (например, 16)
  ```

### 2. Концептуальная модель для сессий пользователей

#### Основная таблица сессий
```cql
CREATE TABLE user_sessions (
    session_id UUID,           -- Clustering Key
    user_id UUID,
    created_at timestamp,
    last_activity timestamp,
    ip_address inet,
    user_agent text,
    geo_zone text,
    session_data map<text, text>,
    PRIMARY KEY ((session_id))
) WITH default_time_to_live = 86400;
```

#### Индексная таблица для поиска по user_id
```cql
CREATE TABLE sessions_by_user (
    user_id UUID,              -- Partition Key
    created_at timestamp,       -- Clustering Key
    session_id UUID,
    last_activity timestamp,
    device_type text,
    PRIMARY KEY ((user_id), created_at)
) WITH CLUSTERING ORDER BY (created_at DESC)
  AND default_time_to_live = 86400;
```

#### Стратегия bucketing для предотвращения горячих партиций
```shell
// Вычисление bucket для равномерного распределения
int calculateBucket(UUID sessionId) {
    long lsb = sessionId.getLeastSignificantBits();
    return Math.abs((int) (lsb ^ (lsb >>> 32))) % 100;
}

// Запись сессии
PreparedStatement insert = session.prepare(
    "INSERT INTO user_sessions (session_id, user_id, created_at, last_activity, ip_address, user_agent, geo_zone, session_data) " +
    "VALUES (?, ?, ?, ?, ?, ?, ?, ?) USING TTL 86400"
);
// 2. Выполнение
session.execute(insert.bind(
    sessionId,   // Первый ? - session_id
    userId,      // Второй ? - user_id
    createdAt,   // Третий ? - created_at
    lastActivity // Четвертый ? - last_activity
    // ... остальные параметры в том же порядке, как в VALUES
));```

### 3. Концептуальная модель для истории заказов

#### Основная таблица с композитным partition key
```cql
-- 1. Сначала создаём UDT для товаров в заказе
CREATE TYPE order_item (
    product_id UUID,
    product_name TEXT,
    quantity INT,
    price DECIMAL
);

-- 2. Основная таблица истории заказов
CREATE TABLE order_history_by_customer_and_month (
    customer_id UUID,          -- Partition Key (1)
    time_bucket TEXT,          -- Partition Key (2) формат: 'YYYY-MM'
    created_at TIMESTAMP,      -- Clustering Key (1)
    order_id UUID,             -- Clustering Key (2)
    total_amount DECIMAL,
    status TEXT,
    delivery_address TEXT,
    payment_method TEXT,
    items LIST<order_item>,    -- Без frozen!
    PRIMARY KEY ((customer_id, time_bucket), created_at, order_id)
) WITH CLUSTERING ORDER BY (created_at DESC) -- Только DESC для всех ключей
  AND compaction = {'class': 'TimeWindowCompactionStrategy',
                    'compaction_window_unit': 'DAYS',
                    'compaction_window_size': 30};```

#### Глобальный индекс для поиска по периодам
```cql
CREATE TABLE orders_by_period (
    time_bucket TEXT,          -- Partition Key ('YYYY-MM-DD')
    created_at TIMESTAMP,       -- Clustering Key
    order_id UUID,
    customer_id UUID,
    total_amount DECIMAL,
    PRIMARY KEY ((time_bucket), created_at, order_id)
) WITH CLUSTERING ORDER BY (created_at DESC);
```

### 4. Анализ и предотвращение "горячих" партиций

#### Метрики мониторинга
Лучше всего использовать встроенные инструменты и стандартные подходы, JMX-метрики и Grafana:
Cassandra через JMX предоставляет сотни метрик. Ключевые для обнаружения hot partition:
* org.apache.cassandra.metrics.Table.{TableName}.ReadLatency / WriteLatency — задержки операций.
* org.apache.cassandra.metrics.Table.{TableName}.ReadRequests / WriteRequests — количество операций в секунду.
* org.apache.cassandra.metrics.Table.{TableName}.LiveDiskSpaceUsed — размер данных на диске.

Настраиваем алерты в Grafana на резкий рост этих метрик для конкретных таблиц.

#### Стратегии предотвращения горячих партиций

| Проблема                       | Решение                             | Реализация                               |
|--------------------------------|--------------------                 |------------------------------------------|
| Популярная корзина             | Sharding bucket по product_id       | PRIMARY KEY ((session_id, bucket_id), product_id) гарантирует уникальность |
| Всплеск сессий                 | Без бакетов, простой доступ         | PRIMARY KEY (session_id) для таблицы user_sessions. Быстрый lookup.        |
| Массовые заказы одного клиента | Time bucketing                      | Разделение по месяцам (YYYY-MM)          |
| Пиковые периоды (Black Friday) | Adaptive bucketing                  | Time bucketing по ДНЯМ или ЧАСАМ          |

### Альтернативы

1. Простое партиционирование без bucketing

Причина отказа:
   * Все товары корзины в одной партиции. 
   Главная причина отказа: HOT PARTITION. Активные сессии в пик нагрузки создадут запредельный RPS на одном узле. 
   Это делает систему нестабильной в самый важный момент.

2. Глобальное партиционирование по времени

Причина отказа:
   * Все заказы дня в одной партиции. 
   Главная причина отказа: НЕ СООТВЕТСТВУЕТ ЗАПРОСУ. 
   Основной запрос к истории заказов — "покажи МОИ заказы", 
   а не "покажи ВСЕ заказы за день". Второй запрос нужен админам, но реже.

**Недостатки, ограничения, риски**

| Риск                                            | Снижение рисков                                                                          |
|-------------------------------------------------|------------------------------------------------------------------------------------------|
| Рост размера партиций со временем               | TTL и time-bucketing                                                                     |
| Горячие партиции                                | Превентивное шардирование на этапе дизайна (bucket_id, мелкие time_bucket). Нагрузочное тестирование                   |
| Потеря данных при сбое                          | RF=3 и + регулярные бэкапы (snapshots) + хранение в удалённом объектном хранилище + учения по восстановлению             |
| Сложность запросов по вторичным атрибутам       | Денормализация: создание отдельной индексной таблицы под каждый частый запрос. Запрет на использование Materialized Views |
| Согласованность данных                          | Паттерн "согласованные индексы" (запись в основную и индексные таблицы в рамках одного логического batch) |
